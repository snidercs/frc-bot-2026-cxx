# PID / Gains Status

A single place to track where every closed-loop controller in the robot stands —
what its gains are, whether they've been properly tuned, and what needs work.

All Phoenix 6 motors use on-controller closed-loop (Slot 0 unless noted).
PathPlanner uses WPILib `PIDConstants` running in the roboRIO.

## Swerve drivetrain (`TunerConstants.h`)

Generated by Tuner X. These are the starting point gains from the swerve generator
and are generally reasonable for a Kraken-powered swerve.

### Steer (position control)
```
KP = 100   KI = 0   KD = 0.5
KS = 0.1   KV = 2.49   KA = 0
StaticFeedforwardSign = UseClosedLoopSign
```

**Status:** Generated values, seem to be working in practice. The `kA=0` is
typical — acceleration feedforward rarely helps steer loops. Worth a quick
Tuner X characterisation run before a real competition to confirm `kV` is
accurate for this specific robot's steer gearbox friction.

### Drive (velocity control — only active during PathPlanner auto)
```
KP = 0.1   KI = 0   KD = 0
KS = 0.0   KV = 0.124
```

**Status:** `kS = 0.0` means static friction is uncompensated. This is
fine for open-loop teleop (`DriveRequestType::OpenLoopVoltage`), but during
PathPlanner auto the drive motors run closed-loop and an uncharacterised `kS`
can cause slow wheel spin-up on direction changes.  
**Action:** Run SysId translation routine (`SysIdQuasistatic` / `SysIdDynamic`
on the drivetrain) to get real `kS` and `kV` values.

## PathPlanner holonomic controller (`drivetrain.cpp`)

```cpp
PPHolonomicDriveController(
    PIDConstants { 10.0, 0.0, 0.0 },  // translation
    PIDConstants { 7.5,  0.0, 0.0 }   // rotation
)
```

**Status:** These are stock numbers from the PathPlanner docs / default examples.
They are not tuned for this robot's mass or inertia. Translation `kP=10` is
aggressive — a robot with lower inertia or slower drive characterisation will
oscillate. Rotation `kP=7.5` may cause heading overshoot on tight turns.  
**Action:**
1. Run a simple straight-line auto and check for translation oscillation.
2. Run a rotate-in-place auto and check for heading overshoot.
3. Tune `kP` down until oscillation disappears, then add a small `kD` for
   damping rather than cranking `kP` back up.

## Turret rotation (`turret.cpp`)

```
KP = 24.0   KI = 0.0   KD = 0.2   KV = 0.12
Sensor-to-mechanism ratio = 10.0
Control mode: MotionMagicVoltage (position)
```

**Status:** Marked `// TODO: tune PID gains` in the source. `kP=24` is high for
a 10:1 gearbox position loop — it is likely stable given the `kD=0.2` damping
term, but overshoot and oscillation near target have not been formally characterised.
`kV=0.12` is a guess; the actual motor velocity constant for this gearbox has not
been measured.  No `kS` term — static friction is uncompensated, which means the
turret may not move at all when the command is very small (dead zone around
setpoint).

**Action:**
1. Add a `kS` term — start around `0.2–0.4` (volts), increase until the turret
   just starts moving from rest on a small error.
2. Run a MotionMagic characterisation: command a step from one limit to the
   other and log position + velocity. Adjust `MotionMagicCruiseVelocity` and
   `MotionMagicAcceleration` (currently not shown — confirm they are set).
3. Reduce `kP` until settling stops oscillating; `kD` can absorb some overshoot
   but it amplifies noise — don't over-rely on it.

> See also [`shooter-and-turret-tuning.md`](../shooter-and-turret-tuning.md) for
> the current value table and shot data log.

## Shooter flywheel (`turret.cpp`)

```
KP = 0.2   KI = 0.0   KD = 0.0   KV = 0.12   KS = 0.25
Control mode: VelocityVoltage
Setpoint range: ~45–64 tps (linear interpolation from distance)
```

**Status:** Marked `// TODO: tune flywheel PID`.  
The `kV = 0.12` value is a placeholder — it has not been derived from a
characterisation run.  For a flywheel, `kV` is by far the most important gain
because it is the primary feedforward that drives the motor to the right speed.
If `kV` is wrong, `kP` has to do all the work and the loop will be slow or
oscillatory.

Two calibration distance/speed points exist (`2.378 m → 45 tps`, `5.0 m → 64
tps`), but the underlying velocity-to-voltage model (`kV`) that determines how
well the motor holds those speeds hasn't been validated.

**Action:**
1. Use SysId or a simple ramp test to get a real `kV`: apply a known voltage,
   measure steady-state velocity, then `kV = volts / velocity_rps`.
2. With correct `kV`, `kP=0.2` may be plenty — test spin-up time and steady-
   state error at both calibration points.
3. Consider `kA` (acceleration feedforward) if spin-up time matters for cycle
   time (faster spin-up = faster re-acquire between shots).
4. More shot distance/speed data points — the two-point linear interpolation is
   fragile for anything near the extremes.

## Uptake (`turret.cpp`)

```
KP = 0.2   KI = 0.0   KD = 0.0   KV = 0.12   KS = 0.2
Setpoint: 100 tps (constant)
Control mode: VelocityVoltage
```

**Status:** Marked `// TODO: tune uptake PID`. These are copy-pasted from the
shooter flywheel. The uptake is a lower-load roller, so `kV` is almost certainly
wrong for this motor/gearbox (the flywheel and uptake have different loads and
likely different gear ratios).

**Action:**
1. Confirm the uptake gear ratio and whether 100 tps is the right target — this
   number has not been validated against actual game piece feed timing.
2. Quick ramp test to estimate `kV` independently from the shooter.
3. If the uptake purely needs to be "fast enough before the shot", open-loop
   voltage control (`VoltageOut`) is simpler and perfectly adequate — only use
   velocity control if exact speed matters for consistent note delivery.

## Intake top & bottom (`intake.cpp`)

```
KP = 0.1   KI = 0.0   KD = 0.0   KV = 0.12
Setpoint: 50 tps (constant)
Control mode: VelocityVoltage (m_velocityRequest)
Top motor: CounterClockwise_Positive
Bottom motor: Clockwise_Positive (inverted)
```

**Status:** `kV=0.12` is the same placeholder used everywhere. `kP=0.1` is very
low — if `kV` undershoots, the proportional term alone may not hold 50 tps under
game-piece load.

The intake also has a `VoltageOut` control request (`m_voltageRequest`) and a
`kIntakeVoltage` constant, suggesting the code was originally written for
open-loop voltage and velocity mode was added later. It's worth confirming
which control request is actually used in each intake command.

**Action:**
1. Check whether intake commands call `m_voltageRequest` or `m_velocityRequest`
   — there may be dead code.
2. If velocity mode is needed (e.g., for consistent intake under varying loads),
   characterise `kV` on the intake motors specifically.
3. If open-loop is sufficient (intake just needs to spin), remove the velocity
   control path and simplify.

## Cross-cutting issues

### Every Phoenix 6 velocity/position loop shares `kV = 0.12`

This value was copied across turret, uptake, intake, and shooter without
individual characterisation. The right `kV` is specific to each motor's load,
gearbox, and measurement units (tps vs rpm vs rad/s). Getting all four to a
real `kV` will likely fix the majority of steady-state error on every loop.

### No `kA` anywhere

Acceleration feedforward (`kA`) is unset on all loops. For the flywheel it
is worth testing — it speeds up spin-up. For the turret MotionMagic loop,
`kA` can make acceleration tracking smoother but is rarely critical.

### `kI` is zero everywhere — keep it that way

Integral gain introduces windup risk in a position or velocity loop running on
a real robot with hard stops (turret) or variable loads (intake). Zero `kI` is
the right default. If there is persistent steady-state error after fixing `kV`,
increase `kP` or `kS` before reaching for `kI`.

### SysId routines exist but have not been run

`CommandSwerveDrivetrain` has three SysId routines wired up
(`m_sysIdRoutineTranslation`, `m_sysIdRoutineSteer`, `m_sysIdRoutineRotation`).
These produce the log data needed to get real `kS`, `kV`, `kA` for the
drivetrain. Running them before the next competition would close the biggest
tuning gap on the robot.

## Recommended tuning order

1. **Drivetrain SysId** — biggest impact, data directly feeds PathPlanner auto quality.
2. **Shooter flywheel `kV`** — single ramp test, immediately improves shot consistency.
3. **Turret `kS`** — small change, fixes the dead-zone-around-setpoint problem.
4. **PathPlanner PID** — simple step-response test in the gym, no characterisation hardware needed.
5. **Uptake / intake `kV`** — low risk, do this if note feeding feels inconsistent.
